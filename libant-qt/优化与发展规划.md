# libant-qt 优化与发展规划

## 1. 文档目的

这份文档不讨论抽象愿景，目标是把 `libant-qt` 未来一段时间内该怎么收敛、补齐和演进，整理成可执行的工程路线。

适用范围：

- 组件库架构优化
- API 稳定性建设
- 主题、图标、样式体系收敛
- demo / 文档 / 测试 / 发布链路完善

---

## 2. 当前现状判断

### 2.1 已经具备的基础

- 目录已经按 `core / input / view / layout / navigation / overlay / feedback / display` 分类。
- `DesignSystem`、`IconProvider`、`StyleSheet` 已经形成了基础设施雏形。
- `libant-qt-demo` 和 `libant-qt-demos` 已经从“库源码”里分离出了一部分 demo 职责。
- 构建已统一到 `xmake`，项目边界比早期清晰很多。

### 2.2 当前主要问题

1. 库和 demo 的边界还不够稳定。
2. 控件 API 风格不完全统一，命名、参数组织、默认行为还带有历史痕迹。
3. 主题系统更多是“颜色集中管理”，离真正的 design token 体系还有距离。
4. `StyleSheet` 还是片段式工具集合，缺少系统性的样式层协议。
5. 缺少明确的组件成熟度定义，不容易判断哪些控件适合正式业务接入。
6. 缺少自动化回归测试，当前更多依赖 demo 人工冒烟。
7. 文档现在偏“代码说明”，还不够像一个可持续维护的组件库文档站。
8. 发布、版本、兼容性策略还没有真正建立起来。

---

## 3. 未来目标

未来的 `libant-qt` 应该逐步变成一个具备以下特征的 Qt Widgets 组件库：

- 边界清晰：库只保留通用能力，场景装配留在 demo 或业务层。
- API 稳定：新增控件和旧控件有统一的命名、状态、主题接入方式。
- 样式可控：主题切换、字体、间距、圆角、阴影、图标都可以系统化管理。
- 可验证：每类关键控件都有最小化测试和稳定 demo 页面。
- 可交付：具备版本号、变更记录、兼容说明和接入文档。

---

## 4. 总体策略

建议用“四层模型”继续收敛代码：

### 4.1 Core 层

职责：

- 设计 token
- 主题与颜色
- 图标语义
- 基础样式生成
- 通用动画/效果工具

对应目录建议：

- `src/core/`

重点要求：

- 不依赖业务场景
- 不直接耦合 demo 页面资源
- 对外接口尽量稳定

### 4.2 Primitive 层

职责：

- 作为最基础的交互控件和容器控件
- 强调单一职责

对应范围：

- `input/`
- `layout/`
- `navigation/`
- `overlay/`

重点要求：

- 每个控件都要有明确的状态模型
- 构造参数和 setter 规则统一
- 可单独测试，不依赖复杂页面装配

### 4.3 Composite 层

职责：

- 在库中保留“通用组合控件”
- 例如卡片、空态、带状态的展示区、可复用信息块

对应范围：

- `feedback/`
- `display/`
- 少量真正可复用的 view 组件

判断标准：

- 如果一个组件脱离当前 demo 页面仍然有复用价值，才保留在库里。
- 如果强依赖具体页面流程、业务话术或某个演示链路，就不要继续放在库里。

### 4.4 Showcase 层

职责：

- 验证组合效果
- 展示推荐用法
- 充当视觉回归入口

对应项目：

- `libant-qt-demo`
- `libant-qt-demos`

重点要求：

- demo 不反向定义库 API
- demo 负责展示最佳实践，而不是承载临时逻辑垃圾场

## 5. 分阶段路线

## Phase 1: 稳定库边界

目标：先把“什么应该在库里，什么应该留在 demo”定住。

建议动作：

1. 逐个审查 `display/`、`feedback/`、`view/` 内的组件。
2. 为每个组件打标签：
   - `stable`
   - `experimental`
   - `demo-only`
3. 把明显属于页面场景装配的组件继续迁出到 demo。
4. 为保留在库里的组件补一份最小职责说明。

交付标准：

- 形成一份“组件清单 + 成熟度表”。
- README 和代码文档里明确哪些组件可正式复用。

## Phase 2: 统一 API 风格

目标：降低使用成本，减少“每个控件都像不同作者写的”这种割裂感。

建议动作：

1. 统一构造函数风格。
2. 统一以下命名：
   - `setText`
   - `setIconRole`
   - `setStatus`
   - `setVariant`
   - `setSizeMode`
3. 统一信号命名和语义。
4. 统一控件默认尺寸、内边距、字号基线。
5. 为复杂控件补“推荐初始化顺序”。

交付标准：

- 新控件模板固定下来。
- 旧控件逐步兼容，不一次性做破坏式重写。

## Phase 3: 建立设计令牌体系

目标：把 `DesignSystem` 从“主题单例”推进成真正的 token 中心。

建议动作：

1. 把颜色、间距、圆角、边框、字号、阴影分成独立 token 组。
2. 避免业务层和组件层继续散落 magic number。
3. 让 `StyleSheet` 只消费 token，而不是直接接受大量裸色值。
4. 给亮色 / 暗色主题建立统一 token 映射表。
5. 为图标尺寸、控件高度建立统一等级系统。

建议输出：

- `ThemeTokens`
- `TypographyTokens`
- `SpacingTokens`
- `ElevationTokens`

交付标准：

- 新增控件不再直接硬编码大量颜色和尺寸。
- 主题切换改动能集中在 token 层完成。

## Phase 4: 收敛样式系统

目标：把 `StyleSheet` 从零散工具函数，升级为更可靠的样式协议层。

建议动作：

1. 区分“控件逻辑”和“样式生成”。
2. 为按钮、输入框、Tab、卡片、弹层定义标准 style recipe。
3. 对能用 QStyle/QPalette 的场景优先走原生机制。
4. 对必须走 QSS 的场景集中生成，避免页面直接拼接长字符串。
5. 为高频控件建立变体体系：
   - primary
   - secondary
   - ghost
   - danger
   - success

交付标准：

- 常用控件有稳定的视觉变体接口。
- 页面层不再手写大量样式字符串。

## Phase 5: 测试与回归体系

目标：把“看 demo 靠肉眼检查”提升到“可重复验证”。

建议动作：

1. 为 core 层补单元测试：
   - 主题切换
   - 图标角色映射
   - 样式片段生成
2. 为关键控件补最小行为测试：
   - 输入变更
   - 状态切换
   - 页码变化
   - 弹层显隐
3. 为 demo 建立回归清单：
   - 字体
   - 图标
   - 暗黑模式
   - 高 DPI
   - 中文文本
4. 后续可补截图回归或 golden image 校验。

交付标准：

- 至少具备 core 层和关键交互控件的自动化基础测试。
- demo 运行成为测试补充，而不是唯一手段。

## Phase 6: 文档和发布体系

目标：让组件库具备被团队长期消费的条件。

建议动作：

1. 为每类组件补统一文档模板：
   - 适用场景
   - 最小示例
   - 状态说明
   - 常见坑
2. 给 `libant-qt-demos` 明确定位为“分类文档入口”。
3. 给 `libant-qt-demo` 明确定位为“场景化回归入口”。
4. 维护 `CHANGELOG.md`。
5. 建立版本约束：
   - breaking changes
   - deprecation
   - migration notes

交付标准：

- 新增控件必须同时落 demo 和文档。
- 版本升级时有明确迁移说明。

## 6. 组件优先级建议

建议把后续投入分成三档：

### P0: 优先做稳

- `DesignSystem`
- `IconProvider`
- `StyleSheet`
- `AntButton`
- `AntInput`
- `AntComboBox`
- `MaterialLineEdit`
- `MaterialTabWidget`
- `PopupWidget` / `PopupViewController`
- `AntMessage` / `AntMessageManager`

原因：

- 这些是复用频率最高、最容易形成连锁影响的基础件。

### P1: 优先做体验和组合能力

- `NoDataWidget`
- `SkeletonWidget`
- `PaginationWidget`
- `CardWidget`
- `TagWidget`
- `AnimatedNumber`
- `GlassWidget`

原因：

- 这些组件直接决定库的视觉表达力和场景完成度。

### P2: 优先做扩展和特色件

- `AntChatListView`
- `AntProfileTable`
- `AntTreeView`
- 轮播类组件
- 更复杂的 overlay / controller 能力

原因：

- 这些更适合在基础体系稳定之后再持续增强。

---

## 7. 推荐工作机制

建议以后每新增或重构一个控件，都强制走下面这条链：

1. 先明确它属于库还是 demo。
2. 再定义状态、事件、尺寸和主题接入点。
3. 补最小 demo。
4. 补文档。
5. 对核心能力补测试。
6. 最后再允许业务接入。

这样能避免库越来越大，但质量越来越不可控。

---

## 8. 未来 3 个里程碑建议

### Milestone A: 可复用基础库

目标：

- 基础控件 API 统一
- 主题 / 图标 / 样式入口稳定
- demo 和库边界清楚

验收标准：

- 新页面开发能主要依赖库里的基础件完成。

### Milestone B: 可验证组件库

目标：

- 补齐核心测试
- demo 页面具备稳定回归价值
- 文档能支撑团队内部复用

验收标准：

- 每次改动不会只能靠手工点一遍来确认是否回归。

### Milestone C: 可发布的团队级组件库

目标：

- 版本化
- 变更说明
- 迁移策略
- 更完整的组件规范和接入说明

验收标准：

- `libant-qt` 不只是当前仓库里的代码集合，而是真正能长期演进的组件库产品。

---

## 9. 最后结论

`libant-qt` 下一阶段最重要的不是继续无节制加控件，而是先把下面四件事做稳：

1. 库和 demo 的边界
2. API 和样式的一致性
3. 主题 token 体系
4. 测试、文档、版本化

如果这四件事稳住，后面再加新控件，成本会明显下降；如果这四件事不稳，组件越多，维护成本只会越来越高。
